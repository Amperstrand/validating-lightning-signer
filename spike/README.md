# electrum-vls-spike

Fork-local spike (never for upstream): prove VLS can mirror the Electrum
wallet's lightning key derivation, as groundwork for running Electrum
"mostly as is" against a validating VLS oracle.

## What M1 proves

`spike/src/lib.rs` implements `KeyDerive` (the same trait behind vls-core's
`KeyDerivationStyle::{Native,Ldk,Lnd}`) with Electrum's scheme, plus the
anchors-context derivations the trait cannot express. The KAT in
`spike/tests/kat.rs` checks every value against vectors generated by
Electrum's own unmodified code (`spike/python/gen_vectors.py` against a
spesmilo/electrum checkout).

Byte-for-byte agreement across 3 cases (each: wallet keys from `m/67'/`,
channel basepoints from `channel_seed` as a fresh BIP32 root, anchors
funding keys we/they opened, payment basepoint, and 73 shachain
secrets/points over scattered ctns up to `START_INDEX-1`):

- standalone derivation functions
- the `KeyDerive` trait implementation (`ElectrumKeyDerive`)
- BOLT-3 pubkey blinding vs LDK's semantics
- vls-core's `chan_utils::build_commitment_secret` (LDK 0.2.4) — **matches
  Electrum's shachain exactly, including the `START_INDEX - ctn` index
  convention. No per-commitment override is needed in M2.**

## Findings

- BIP-340 tagged hashes digest the tag twice; getting this wrong is easy and
  the KAT catches it (it did).
- `vls-core`'s lib name is `lightning_signer` (historical), not `vls_core`.
- Wallet-level inputs VLS needs at setup: wallet seed entropy (for `m/67'/`
  families) and the per-channel `channel_seed` (random, stored in Electrum's
  wallet DB). The latter fits the `keys_id` slot of `KeyDerive::channel_keys`.
- Anchors funding/payment keys need channel context (remote node id,
  nlocktime or remote funding pubkey) that the trait lacks; the M2 setup seam
  should call the standalone functions instead.
