# electrum-vls-spike

Fork-local spike (never for upstream): prove VLS can mirror the Electrum
wallet's lightning key derivation, as groundwork for running Electrum
"mostly as is" against a validating VLS oracle.

## What M1 proves

`spike/src/lib.rs` implements `KeyDerive` (the same trait behind vls-core's
`KeyDerivationStyle::{Native,Ldk,Lnd}`) with Electrum's scheme, plus the
anchors-context derivations the trait cannot express. The KAT in
`spike/tests/kat.rs` checks every value against vectors generated by
Electrum's own unmodified code (`spike/python/gen_vectors.py` against a
spesmilo/electrum checkout).

Byte-for-byte agreement across 3 cases (each: wallet keys from `m/67'/`,
channel basepoints from `channel_seed` as a fresh BIP32 root, anchors
funding keys we/they opened, payment basepoint, and 73 shachain
secrets/points over scattered ctns up to `START_INDEX-1`):

- standalone derivation functions
- the `KeyDerive` trait implementation (`ElectrumKeyDerive`)
- BOLT-3 pubkey blinding vs LDK's semantics
- vls-core's `chan_utils::build_commitment_secret` (LDK 0.2.4) — **matches
  Electrum's shachain exactly, including the `START_INDEX - ctn` index
  convention. No per-commitment override is needed in M2.**

## Findings

- BIP-340 tagged hashes digest the tag twice; getting this wrong is easy and
  the KAT catches it (it did).
- `vls-core`'s lib name is `lightning_signer` (historical), not `vls_core`.
- Wallet-level inputs VLS needs at setup: wallet seed entropy (for `m/67'/`
  families) and the per-channel `channel_seed` (random, stored in Electrum's
  wallet DB). The latter fits the `keys_id` slot of `KeyDerive::channel_keys`.
- Anchors funding/payment keys need channel context (remote node id,
  nlocktime or remote funding pubkey) that the trait lacks; the M2 setup seam
  should call the standalone functions instead.

## M2: bridge (done)

`spike/src/bridge.rs` embeds a vls-core `Node` and serves JSON-lines RPC over a
Unix socket: `node_info`, `new_channel`, `setup_channel`, `confirm_funding_lock`,
`get_per_commitment_point`. This uses the two fork-local vls-core changes:
`KeyDerivationStyle::Electrum` (derive.rs) and `Node::new_channel_with_keys_id`
(node.rs), which routes an externally-provided keys_id (Electrum's
`channel_seed`) into key derivation.

Verified twice: `tests/bridge_e2e.rs` (Rust) and `python/test_bridge_client.py`
(Python — the Electrum-shaped consumer path). Over the socket, the bridge's
node_id, channel basepoints, and per-commitment points equal Electrum's own
values from the KAT vectors.

    cargo build -p electrum-vls-spike --bin vls_bridge
    spike/python/.venv/bin/python spike/python/test_bridge_client.py

## M3: tap harness (done)

`python/electrum_tap.py` wraps `Channel.get_secret_and_point` (fires during
signing, revocation and sweeps) and mirrors every LOCAL per-commitment point
into the bridge. `python/test_tap_mirror.py` builds REAL Electrum channels
with Electrum's own test helpers (`tests/lnhelpers.py`), registers both
sides, runs direct ctn 0..2 checks plus a full commitment round
(sign -> receive_new_commitment -> revoke -> receive_revocation), and asserts
zero divergences: 12 point comparisons, 0 divergences, all basepoints equal.

Discovery: both sides of a channel share `channel_id` (derived from the
funding outpoint), so the tap registry is keyed by `channel_seed` — relevant
to any future live plugin that taps both sides in one process.

    spike/python/.venv/bin/python spike/python/test_tap_mirror.py

## M4: signing cross-check (done)

The "VLS validates" milestone: VLS signs Electrum's **actual** commitment
transaction and the signature verifies against Electrum's own BIP-143 sighash
(`sha256d(commitment.serialize_preimage(0))` — the same computation
`receive_new_commitment` verifies with). Self-validating: Electrum's own
signature is verified first as a sanity gate. Signature BYTES differ between
`electrum_ecc` and `rust-secp` (nonce derivation), so verification — not byte
equality — is the check.

Route taken (after dead ends, all documented):
- The semantic `sign_counterparty_commitment_tx_phase2` route diverges **by
  construction**: Electrum's commitments have sorted outputs, privacy-mixed
  locktime/sequence, and a p2wsh-wrapped to_remote
  (`<pubkey> CHECKSIGVERIFY 1 CSV`) that VLS's canonical recomposition cannot
  reproduce.
- The raw-tx route (`sign_counterparty_commitment_tx`, channel.rs) decodes the
  actual tx via per-output witscripts. Strict policy then rejects it at the
  `recomposed tx mismatch` gate; the fork's permissive mode (splice-resume
  workaround) falls through and signs the HOST tx verbatim. The bridge builds
  its node with the fork-local `make_permissive_services()` (test_utils).

Findings banked along the way:
- VLS's counterparty commit numbering is electrum ctn + 1; the harness syncs
  state via the pub testing setters (`sync_commitment_state` bridge method).
- The counterparty per-commitment point must be derived from its OWN seed
  (`get_per_commitment_secret_from_seed(bob_seed, START_INDEX - ctn)`);
  to_local witscripts are matched by sha256 program against a candidate
  matrix (both basepoint-party assignments, both delay sources).
- `PartialTransaction.serialize()` returns PSBT;
  `serialize_to_network(include_sigs=False)` gives the network hex the Rust
  side needs.
- LDK's `make_funding_redeemscript` sorts keys — order-independent.

## M5: live regtest channel (done)

The end-to-end proof: a real Electrum daemon on regtest, a real channel to a
CLN node, real invoice payments — with VLS mirroring the channel live and
every commitment signature it produces **verifying against Electrum's own
BIP-143 sighash**. Final state: `signature cross-checked ctn=14/15,
comparisons=12, divergences=0`.

Topology: bitcoind + electrumx + CLN on ai-legion (docker, ports tunneled
over ssh through a jumphost), vls_bridge + tapped Electrum daemon on the
workstation. `run_electrum_tapped.py` wraps the daemon entry, installs the
live tap (`ensure_registered` mirrors channels lazily on first use;
`sign_next_commitment` is wrapped for the signature cross-check).

Two live-only seams found and fixed VLS-side (the spike thesis):
- **Funding-key seam**: live anchors channels derive the multisig funding key
  from the wallet `funding_root_secret`, not from `channel_seed` (the M3/M4
  harness masked this by passing `multisig_funding_keypair=None`). Fix:
  `new_channel_with_keys_id` accepts a funding override
  (`set_funding_key_for_testing` also refreshes the construction-cached
  holder pubkeys — the cache is a real trap).
- **Mid-life numbering**: a live channel registers at ctn N, not 0. Fix: the
  tap fast-forwards holder/counterparty numbering at registration and before
  each cross-check; peek-ahead point queries past the synced window are
  tolerated.

Operational notes: `--server` is a per-subcommand option (must follow
`daemon`); `use_gossip=true` config is required for non-trampoline peers
(CLN); `PartialTransaction.serialize_to_network(include_sigs=False)` for the
raw route; background daemons must run in a real terminal (herdr pane) —
shell-tool timeouts kill their process groups.

## M5.1: payment soak (done)

12-payment soak through the live channel (9 paid, 3 ssh-timing invoice
misses — channel itself flawless): commitment numbers advanced ctn 15→33
(**18 live commitment rounds**), cross-check comparisons 12→**116**,
**divergences=0 throughout**. Every VLS commitment signature verified
against Electrum's own BIP-143 sighash.

Also explored: CLN v26.06 `setchannel` sets only routing fees — commitment
feerate updates are funder-side (Electrum), with no deterministic regtest
trigger without extra plumbing; and `request_force_close` against a
cooperative peer negotiates a mutual close (the unilateral justice/sweep
path needs an unresponsive peer — M6 material).

## M6: unilateral close + sweep (done)

Drove the unilateral path end-to-end: CLN `close … unilateral` broadcast its
commitment (mempool), Electrum's watcher detected the foreign ctx, channel
went CLOSED after 3 confirmations, and the to_remote sweep landed (0.049 BTC
unconfirmed, anchors CSV path).

**Finding (empirical)**: the tap emitted zero lines during the sweep — the
anchors to_remote sweep signs with the static **payment basepoint**, which
bypasses the per-commitment surface the tap wraps
(`get_secret_and_point`/`sign_next_commitment`). This is the documented
anchors payment-basepoint seam, now confirmed on-chain: in a
VLS-holds-keys deployment, this sweep would need VLS-side derivation
support (`derive_payment_basepoint(static_secret, funding_pubkey)`).

Also learned: Electrum's `request_force_close` asks the REMOTE to close
(REQUESTED_FCLOSE) — the local unilateral lever is the peer's, so the M6
flow used CLN-side `close 1` (unilateral timeout).

## M7a: live revocation validation (done)

The tap now wraps `Channel.receive_revocation` and forwards every revealed
remote per-commitment secret to VLS's `validate_counterparty_revocation`
(bridge RPC). On live payments: `tap: revocation validated ctn=9..12`
interleaved with signature cross-checks, **divergences=0** — VLS
chain-validates (shachain) every revocation the peer reveals, on real
traffic. This is the justice-path foundation: with the remote's secrets in
its shachain, VLS holds everything it needs to produce justice signatures
for a stale-state broadcast (M7b, needs a developer CLN build +
snapshot/restore dance).

## M7b: stale-state broadcast → justice (done)

The full watchtower scenario, end-to-end on live infra:

1. Stopped CLN mid-channel and snapshotted its state (docker cp, 388K).
2. Advanced the channel with payments — Electrum collected revocations
   (`tap: revocation validated ctn=14..16`; CLN ended 34 revocations
   ahead of its snapshot).
3. Restored the stale CLN state (helper container on the volume), restarted
   — CLN immediately detected the desync on reestablish
   (`bad reestablish revocation_number: 0 vs 34`), went ONCHAIN, and
   unilateral-closed with the **revoked** commitment
   (`112ba977…`, confirmed).
4. Electrum's watcher: FORCE_CLOSING → justice sweep broadcast and
   confirmed (`131e326f…` spending `112ba977:1`).

**Witness forensics** (the decisive evidence): the sweep's input witness is
`[sig(71), empty(0), script(75)]` — the **empty item is the IF-true branch
selector** of the to_local script, i.e. the spend used the **revocation
key**. That is the justice path, on-chain, confirmed.

**Tap finding (consistent with M6)**: the tap was silent through the entire
justice flow — lnsweep's justice builders sign with
`derive_blinded_privkey(revocation_basepoint_secret, remote_pcp_secret)`
directly, never touching the wrapped surfaces. The next increment is
therefore precisely scoped: wrap lnsweep's justice builders + bridge RPCs
for VLS's `sign_justice_revoked_output`/`sign_justice_revoked_htlc` — with
M7a, VLS already holds every secret needed (shachain-validated).

## M7c-v2: justice replay with instrumentation (done)

Instrumented `extract_ctx_secrets` in the tap (prints ctn,
oldest_unrevoked, and classification for every call) and added explicit
prints to every silent path in `cross_check_justice`. Re-ran the full
stale-state dance on channel #5 (wider gap: 10 payments post-snapshot,
channel at ctn 23 vs snapshot at ~5).

**Results**:
- **CTN instrumentation works**: `tap: CTN ctn=5 oldest_unrevoked=23 →
  BREACH` — the stale ctx IS classified as revoked (the M7c-v1 gap was too
  narrow: ctn 7 vs oldest 7 → "current").
- **Justice wrap fires**: `tap: justice wrap CALLED` — the module-level
  patch on `lnsweep.sweep_their_ctx_justice` intercepts correctly.
- **cross_check_justice runs**: ENTERED → ensure_registered → bridge call —
  all the way to the to_local output matching.
- **Two bugs found and fixed in the tap's cross-check**:
  1. Missing `ensure_registered(chan)` → channel not in bridge dict →
     silent return. Fixed: registration + explicit print.
  2. `to_self_delay` from the WRONG side (`REMOTE` instead of `LOCAL`) —
     Electrum's `sweep_their_ctx_justice` uses the non-broadcaster's
     (LOCAL/us) delay. Fixed.
- **Root cause FOUND — shachain bucket mismatch**: the shachain stores
  secrets for ctns {20, 17, 19, 7, 15} in buckets {0,1,2,3,4}. For the
  stale ctx at ctn 5, the required bucket is 2 (XOR bit analysis).
  Bucket 2 contains the secret for ctn 19 — but the lower bits DISAGREE
  (5=0b00101 vs 19=0b10011). The `retrieve_secret` derivation chain
  from ctn 19's secret to ctn 5's position requires multiple hash steps
  that the bucket structure doesn't support. Electrum's shachain
  returns a derived value (not throwing UnableToDeriveSecret), but the
  resulting pcp doesn't match CLN's actual commitment. This is a
  genuine shachain derivation-chain gap — the stored secrets don't
  cover ctn 5's position, yet `retrieve_secret` doesn't fail cleanly.
  Both Electrum's justice sweep and the tap's cross-check correctly
  fail to match (SCRIPT-AGREE between both derivations, but neither
  matches the on-chain output).

**The instrumentation (committed) is permanent yield**: CTN classification,
REV-KEY equivalence, SCRIPT-AGREE, SPK-DIFF, and the shachain bucket dump —
the complete diagnostic chain from classification to output matching.
